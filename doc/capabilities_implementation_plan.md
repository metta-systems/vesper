# Capability implementation plan

The design authority is [Nucleus capabilities: design contracts](nucleus_capabilities.md). This checklist turns those contracts into dependency-ordered work across `libs/object`, `libs/syscall`, `kernel/nucleus/src/api`, `kernel/nucleus/src/objects`, and the nucleus entry/scheduler/backend code.

This is a TODO list, not a claim of implementation. The reference and initial checklist have been created; approval, reconciliation, and code validation remain work. Mark an item `- [x]` only after its stated outcome is implemented/reviewed and the relevant validation has actually passed. Record blocked or unrun validation rather than checking it off.

## Working rules

- Select a small, explicitly scoped item or coherent group of items; do not execute the entire backlog merely because this file exists.
- Read the reference and relevant decision-register entries first. Resolve prerequisite decisions with the maintainer; do not silently promote a recommendation to a contract.
- Inspect module declarations, feature/target gates, call sites, and current local edits. Distinguish excluded sketches from reachable behavior.
- Change a contract here and in the reference before intentionally implementing a different ABI or semantic model.
- Complete the affected shared definitions, client encoding/decoding, kernel authorization, state transitions, and tests together. Unsupported operations must remain explicit errors.
- Preserve user work. This repository uses JJ: no raw Git, commits, history changes, new changes/branches, or pushes by default. Version-control mutation requires an explicit request.
- Use **`just` for project build, test, formatting, and lint workflows**. Read the current `Justfile`; do not replace its recipes with hand-assembled Cargo/rustfmt commands or assume a native build validates the embedded target.
- Keep completion evidence with the checklist or in the task report: recipes/checks actually run, outcomes, limitations, and follow-up blockers. Supplemental diagnostics and dry runs do not count as completed project validation.
- Keep [`doc/object_types/`](object_types/) current with every capability refactor: when a refactor invalidates a per-kind document, replace the no-longer-valid content with new data instead of layering amendments on top of stale text. The catalogue tables, wire IDs, operation lists, and status columns must describe the implemented reality after each slice. Documentation states the **current contract only** — no selection dates, no "selected/moved/renamed from" history, no "formerly…" chains; the contract and this plan carry the history.
- There is no previous version of anything: once a change is approved, preserve no backwards compatibility, migration path, deprecated alias, or legacy behavior. Functionality can be completely removed and replaced when necessary; update all consumers in the same slice.

## Phase 0 — Refactoring resolutions from the object-types review

The per-kind reference documentation in [`doc/object_types/`](object_types/) was generated against the current implementation and compared with the desired-capability notes. That review produced refactoring changes that must land **before** the remaining phase work. Each numbered entry below records one maintainer-approved change and its context; the affected items in Phases 1–7 and the final-integration section are updated alongside so the plan stays consistent with what Phase 0 changes.

- [x] 0.1 — Split and rename `Domain` into `AddressSpace` and `Thread` (2026-09-21, maintainer resolution from the object-types review). Implemented and validated the same day — see the slice validation below.
  - `Domain` splits into two objects. **`AddressSpace`** holds the translation root — Vesper's equivalent of seL4's VSpace. **`Thread`** is the remainder of the former `Domain` (execution context, scheduling/pending state, DCB relationship).
  - A `Thread` holds a capability to its `AddressSpace` and a capability to its `KeyTable` — Vesper's capability-slot namespace.
  - Resolved (2026-09-21, maintainer decisions): **AddressSpace is an arch kind** — seL4's VSpace is arch-side there, so the reserved `VSpace` (index 2, wire `0x82`) is renamed `AddressSpace` and activated as the mapping-context object; `vspace.rs` becomes `address_space.rs`. Core `Domain` is removed entirely: `KeyTable` moved 3 → 2 and `Thread` takes 3 (maintainer-specified catalogue; coordinated rebuild, no compatibility numbering). Operation division: `AddressSpace.Activate` 0 (translation-context installation, current-caller-restricted) and `AddressSpace.Retire` 1 (new, selected 2026-09-21 — whole-ASID invalidation, ASID release to the originating pool, root/ASID fields cleared, pool slot reclaimed; root must already be uninstalled via `PageTable.Unmap`) are arch-dispatched; `Thread.Retire` 4 keeps the thread-side teardown (cancel pending, purge wakeup, reclaim the Thread slot); `Thread.Grant` 1 / `Suspend` 2 / `Resume` 3 stay explicit `InvalidOperation` (Phase 7). Representation: `AddressSpace { translation_root, asid }` and `Thread { keytable_addr, address_space: ObjectId, context }`, both pooled. D5 rework direction recorded: remove `DcbPages`/`DcbView`; scheduler-owned pages are shared to the kernel by `Scheduler.ShareRegion`, with `Scheduler = 9`, `Brand = 10`, a mapped Frame argument, fixed-stride Thread records, derivable hierarchical schedulers, and root-scheduler bootstrap before scheduling. Scheduler-writable record pages remain separate from kernel-private TCB state; exact field split and table mechanics remain open. Doc updates: `core/domain.md` → `core/thread.md`, `arch/vspace.md` → `arch/address_space.md`, `arch/asid.md` → `arch/asid_control.md`, README catalogue tables and invocation diagram regenerated, `key_table.md` wire value 3 → 2.
- [x] 0.2 — Replace the reserved `ASID` architecture kind with `ASIDControl` (2026-09-21, maintainer resolution from the object-types review). Implemented and validated together with 0.1 — see the slice validation below.
  - An ASID is a hardware naming value bound to an `AddressSpace` (post-0.1), not an independently capabilitied object — it has no separate capability, so it must not be a wire type. The reserved `ASID` kind (arch index 4, wire `0x84`) is removed and replaced by **`ASIDControl`** at the same index.
  - `ASIDControl` is the capability-protected control point over the ASID namespace — the expected home for pool creation/partitioning (seL4-style), currently recorded as the open multi-pool partitioning of the 16-bit ASID space. Its operation schema is open; the kind stays reserved/unsupported until that contract is specified.
  - Resolved (2026-09-21): the maintainer confirmed the numbering — `ASIDControl` keeps arch index 4 (wire `0x84`) — and it lands in the same renumbering slice as 0.1. Doc updates: replace `doc/object_types/arch/asid.md` with `arch/asid_control.md`, update the arch catalogue table and the invocation-model diagram in `doc/object_types/README.md`.

### Domain split, Thread/AddressSpace, and ASIDControl slice validation (2026-09-21)

Implemented the 0.1/0.2 resolutions across every layer, with no compatibility preserved for the prior numbering or the single-Domain model. The catalogues were renumbered exactly as the maintainer specified: core `Domain` (2) removed, `KeyTable` moved 3 → 2, `Thread` took 3; arch `VSpace` renamed `AddressSpace` (index 2) and `ASID` replaced by `ASIDControl` (index 4). The former `Domain` object split into the core `Thread` (`keytable_addr`, checked `address_space` identity, `ExecutionContext`) and the arch `AddressSpace` (`translation_root`, `asid`, behind the new `AddressSpaceObject` trait); `objects/domain.rs` keeps only the DCB machinery (names unchanged until D5). Operation division: `AddressSpace.Activate` 0 (arch dispatch; translation-context installation, current-caller-restricted) and the new `AddressSpace.Retire` 1 (whole-ASID invalidation, ASID release to the originating pool via the new `AsidPoolObject::release`, root/ASID fields cleared, pool slot reclaimed; own-context and root-installed rejections) landed in `api/arch/address_space.rs`; `Thread.Retire` 4 (thread-side teardown via `Nucleus::cancel_thread_pending`) landed in `api/thread.rs`; `Thread.Grant`/`Suspend`/`Resume` stay explicit `InvalidOperation`. `PageTable.Map` root installation, `Frame.Map`, and `ASIDPool.Assign` now target the AddressSpace kind; the frame payload's mapping record names the owning AddressSpace; `PtParent::Root` carries an address-space identity; the scheduler, pending-pool waiters, and `current_thread` are Thread-based. Kickstart carves both pools (threads 2, address spaces 3), creates a boot AddressSpace + boot Thread, installs the self-AddressSpace cap at the renamed `KeySlot::SELF_ADDRESS_SPACE` and a boot-Thread cap, and the boot test exercises the full matrix end-to-end: `Thread.Retire` (rights denial, self-retirement rejection, parked-thread teardown, stale-capability rejection) and `AddressSpace.Retire` (own-context rejection, root-installed rejection, ASID release proven by a rebind receiving the released ASID 2). Userspace gained `ThreadKey`/`ThreadOp` (op 0 was unassigned in this historical slice; the current contract and Phase 6 representation use Thread.Return 0) and `AddressSpaceKey`/`AddressSpaceOp` wrappers; the DCB direction (thread scheduling pages shared with the userspace scheduler, Composite-style) is recorded in the contract under D5. The superseded `api/arch/vspace.rs` and `objects/arch/vspace.rs` sketches were replaced by the real handler/object (their SetRoot/AssignASID/GetASID intent is captured by `PageTable.Map` root, `ASIDPool.Assign`, and the new handler). Docs were replaced, not amended: `core/domain.md` → `core/thread.md`, `arch/vspace.md` → `arch/address_space.md`, `arch/asid.md` → `arch/asid_control.md`, the README catalogue/diagram regenerated, and the mapping-family docs (`frame.md`, `page_table.md`, `asid_pool.md`, `key_table.md`, `untyped.md`, `notification.md`, `event_count.md`) updated to the AddressSpace/Thread vocabulary.

Maintainer foundation decisions (2026-09-06): ordinary keys use implicit caller-table context, with initially 32-bit slot and 32-bit incarnation fields and separate shared-object identity, without freezing total key size permanently. Guarded key-space package (selected 2026-09-23, not yet implemented): the key's low 32 bits become a table-relative address — a userspace-chosen per-table guard in the top `32 − size_bits` bits above the `size_bits`-wide slot index. Guards are namespace values, not secrets — they bind keys to their table rather than hiding entries from a table's own users.

### Guarded key-space package slice validation (2026-09-23)

Implemented the selected guarded key-space package end-to-end. `KeyTable` is now a carved, variable-size object: a 32-byte header (owner, count, capacity exponent — authoritative for internal bounds) followed by `2^size_bits` `KeyEntry` slots and incarnation counters in the same carve (`KeyTable::carve_size`, `KeyTable::initialize` writing/zeroing the whole region); `size_bits` at Retype selects the capacity (1..=20, `InvalidSize` otherwise). The `KeyTablePayload` records `{address, guard, size_bits}` (kernel-visible only, copied verbatim by derivation), and the Retype `x3` word packs the userspace-chosen guard into bits 39:8 above the `size_bits` byte (bits 63:40 reserved zero; every other kind requires bits 63:8 zero; the guard must fit `32 − size_bits` bits). A Retype batch is bounded to 256 objects (`InvalidOperation` otherwise; the transaction's defensive rollback records are stack arrays sized by the bound). ### Protected Procedure Call: Invocation design and migration

Maintainer selection: `Invocation` is a Protected Procedure Call (PPC). It identifies a component API entry point in a target AddressSpace, and the source Thread migrates into that AddressSpace; no server Thread is required. `Invocation.Call` is op `0`, with six `u64` Call inputs in `x2..x7` under the common `CapInvoke` ABI. The target component/export setup selects and publishes a nonempty stack extent when constructing the Invocation. At Call, the target entry SP is 16-byte aligned and checked against that published extent; the extent/headroom inputs use `x5` base, `x6` exclusive end, and `x7` positive minimum headroom as a direct `u64` byte count, representing `[base, end)` and rejecting `base >= end`. Call requires 16-byte-aligned `SP`, `base < SP <= end`, and `SP - base >= M` for positive minimum downward headroom `M` published by the target at CreateInvocation and stored in the Invocation. Its byte-count encoding and alignment are selected: `base`, `end`, and `M` are each multiples of 16 bytes, without requiring page alignment. Construction rejects `M > end - base` before installing a capability; equality is valid. Stack validation uses the selected `InvalidStack` family: `x1` offending `u64` value and `x2` field-specific typed reason, without operand packing. Status 32, the catalogue, reason IDs 1–12 (0 invalid), offending-value rules, stack-predicate order and admission-stage placement are selected in the canonical contract. The kernel checks the published range only, not its page mappings or whole-stack writability. The target SP uses an ABI channel separate from target function arguments; target-entry `x0` and `x1` are two leading dummy arguments ignored by the target, and the six real `u64` inputs stay unchanged in `x2..x7`, without a register shuffle. None carries SP metadata. The integer result payload is two `u64` words, separate from kernel transport status; successful source resumption uses `x0 = SUCCESS (0)`, `x1 = r0`, `x2 = r1`. The common extern-C body return of a repr-C two-u64 struct in x0/x1 is experimental pending end-to-end confirmation. `Thread.Return` is op `0` on the explicit `CurrentReturnOnly` Thread selector; Return SVC inputs are the target-table-local packed Slot(1) key in x0, x1=0 and payload r0/r1 in x2/x3. Return ignores x4..x7; the low-level helper is fallible (Result<Infallible, CapError>). The common adapter routes Err with original payload to a non-returning libOS fault handler; userspace binding is provisionally link-resolved and the five-word extern-C handler ABI is selected, the handler symbol is `vesper_thread_return_fault`, unexpected local SUCCESS uses selected `UnexpectedReturn` status 34. Conservative x0..x17 compiler declarations are selected; x18 is caller-volatile with discarded wrapper clobbers; FP/SIMD is prohibited/trapped for this slice; kernel non-payload GPR/NZCV scrubbing is selected, not implemented/validated. The working Call-time SP transport is provisionally selected as `x9`, read from saved `frame.gpr[9]` in the kernel, and remains unfrozen until end-to-end Call/Return confirms feasibility. Userspace may compose queued rendezvous over Invocation plus Notification/EventCount. The former rendezvous/reply-object model is replaced. The selected relative timeout for Notification.Wait and EventCount.Await remains unchanged.

**Approved representation-only scope:** `KeySlot::THREAD_RETURN` stays Slot(1), all other slots stay unchanged, and kind IDs remain `Thread = 3` / `Invocation = 7`. The Return cap has explicit `CurrentReturnOnly` selector, never `Named(ObjectId)`, with no function/AS/concrete Thread target or Thread-management rights. Named Thread entries do not authorize Return; the current-relative form rejects Grant/Suspend/Resume/Retire and object_id extraction. Ordinary caller-table/SELF, guard, incarnation, bounds and presence checks remain mandatory: no magic raw key or lookup bypass. Any Thread may invoke the same AS-shared sentinel, but only its own current invstk top may be popped; presence is libOS policy. Invocation is Call-only with mandatory `NonZero<u64>` function address, not Option; CreateInvocation zero remains `InvalidPointer`. Opcode zero on an ordinary Invocation is Call, not wrong-form Return; Thread.Return on a named Thread is `InvalidOperation`, and unknown Invocation op 1 is `InvalidOperation` when the Call handler is enabled (kind currently unsupported). No compatibility alias or old Return opcode is retained. Current-contract descriptions below follow the canonical document; older validation is historical evidence only, not validation of this migration.
