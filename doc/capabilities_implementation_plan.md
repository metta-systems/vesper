# Capability implementation plan

The design authority is [Nucleus capabilities: design contracts](nucleus_capabilities.md). This checklist turns those contracts into dependency-ordered work across `libs/object`, `libs/syscall`, `kernel/nucleus/src/api`, `kernel/nucleus/src/objects`, and the nucleus entry/scheduler/backend code.

This is a TODO list, not a claim of implementation. Historical implementation and validation narratives for completed slices live in [`capabilities-completed.md`](capabilities-completed.md); this file retains the active checklist, prerequisites, and concise links to those records. Mark an item `- [x]` only after its stated outcome is implemented/reviewed and the relevant validation has actually passed. Record blocked or unrun validation rather than checking it off.

## Working rules

- Select a small, explicitly scoped item or coherent group of items; do not execute the entire backlog merely because this file exists.
- Read the reference and relevant decision-register entries first. Resolve prerequisite decisions with the maintainer; do not silently promote a recommendation to a contract.
- Inspect module declarations, feature/target gates, call sites, and current local edits. Distinguish excluded sketches from reachable behavior.
- Change a contract here and in the reference before intentionally implementing a different ABI or semantic model.
- Complete the affected shared definitions, client encoding/decoding, kernel authorization, state transitions, and tests together. Unsupported operations must remain explicit errors.
- Preserve user work. This repository uses JJ: no raw Git, commits, history changes, new changes/branches, or pushes by default. Version-control mutation requires an explicit request.
- Use **`just` for project build, test, formatting, and lint workflows**. Read the current `Justfile`; do not replace its recipes with hand-assembled Cargo/rustfmt commands or assume a native build validates the embedded target.
- Keep concise completion evidence in the checklist and move detailed historical records to [`capabilities-completed.md`](capabilities-completed.md): recipes/checks actually run, outcomes, limitations, and follow-up blockers. Supplemental diagnostics and dry runs do not count as completed project validation.
- Keep [`doc/object_types/`](object_types/) current with every capability refactor: when a refactor invalidates a per-kind document, replace the no-longer-valid content with new data instead of layering amendments on top of stale text. The catalogue tables, wire IDs, operation lists, and status columns must describe the implemented reality after each slice. Documentation states the **current contract only** — no selection dates, no "selected/moved/renamed from" history, no "formerly…" chains; the contract and this plan carry the history.
- There is no previous version of anything: once a change is approved, preserve no backwards compatibility, migration path, deprecated alias, or legacy behavior. Functionality can be completely removed and replaced when necessary; update all consumers in the same slice.

## Phase 0 — Refactoring resolutions from the object-types review

The per-kind reference documentation in [`doc/object_types/`](object_types/) was generated against the current implementation and compared with the desired-capability notes. That review produced refactoring changes that must land **before** the remaining phase work. Each numbered entry below records one maintainer-approved change and its context; the affected items in Phases 1–7 and the final-integration section are updated alongside so the plan stays consistent with what Phase 0 changes.

- [x] 0.1 — Split and rename `Domain` into `AddressSpace` and `Thread` (2026-09-21, maintainer resolution from the object-types review). Implemented and validated the same day — see the slice validation below.
  - `Domain` splits into two objects. **`AddressSpace`** holds the translation root — Vesper's equivalent of seL4's VSpace. **`Thread`** is the remainder of the former `Domain` (execution context, scheduling/pending state, DCB relationship).
  - A `Thread` holds a capability to its `AddressSpace` and a capability to its `KeyTable` — Vesper's capability-slot namespace.
  - Resolved (2026-09-21, maintainer decisions): **AddressSpace is an arch kind** — seL4's VSpace is arch-side there, so the reserved `VSpace` (index 2, wire `0x82`) is renamed `AddressSpace` and activated as the mapping-context object; `vspace.rs` becomes `address_space.rs`. Core `Domain` is removed entirely: `KeyTable` moved 3 → 2 and `Thread` takes 3 (maintainer-specified catalogue; coordinated rebuild, no compatibility numbering). Operation division: `AddressSpace.Activate` 0 (translation-context installation, current-caller-restricted) and `AddressSpace.Retire` 1 (new, selected 2026-09-21 — whole-ASID invalidation, ASID release to the originating pool, root/ASID fields cleared, pool slot reclaimed; root must already be uninstalled via `PageTable.Unmap`) are arch-dispatched; `Thread.Retire` 4 keeps the thread-side teardown (cancel pending, purge wakeup, reclaim the Thread slot); `Thread.Grant` 1 / `Suspend` 2 / `Resume` 3 stay explicit `InvalidOperation` (Phase 7). Representation: `AddressSpace { translation_root, asid }` and `Thread { keytable_addr, address_space: ObjectId, context }`, both pooled. D5 rework direction recorded: remove `DcbPages`/`DcbView`; scheduler-owned pages are shared to the kernel by `Scheduler.ShareRegion`, with `Scheduler = 9`, `Brand = 10`, a mapped Frame argument, fixed-stride Thread records, derivable hierarchical schedulers, and root-scheduler bootstrap before scheduling. Scheduler-writable record pages remain separate from kernel-private TCB state; exact field split and table mechanics remain open. Doc updates: `core/domain.md` → `core/thread.md`, `arch/vspace.md` → `arch/address_space.md`, `arch/asid.md` → `arch/asid_control.md`, README catalogue tables and invocation diagram regenerated, `key_table.md` wire value 3 → 2.
- [x] 0.2 — Replace the reserved `ASID` architecture kind with `ASIDControl` (2026-09-21, maintainer resolution from the object-types review). Implemented and validated together with 0.1 — see the slice validation below.
  - An ASID is a hardware naming value bound to an `AddressSpace` (post-0.1), not an independently capabilitied object — it has no separate capability, so it must not be a wire type. The reserved `ASID` kind (arch index 4, wire `0x84`) is removed and replaced by **`ASIDControl`** at the same index.
  - `ASIDControl` is the capability-protected control point over the ASID namespace — the expected home for pool creation/partitioning (seL4-style), currently recorded as the open multi-pool partitioning of the 16-bit ASID space. Its operation schema is open; the kind stays reserved/unsupported until that contract is specified.
  - Resolved (2026-09-21): the maintainer confirmed the numbering — `ASIDControl` keeps arch index 4 (wire `0x84`) — and it lands in the same renumbering slice as 0.1. Doc updates: replace `doc/object_types/arch/asid.md` with `arch/asid_control.md`, update the arch catalogue table and the invocation-model diagram in `doc/object_types/README.md`.

## Phase 4 — Capability storage and domain lifetime

Reference: [identity](nucleus_capabilities.md#vocabulary-and-identity), [lifecycle](nucleus_capabilities.md#copy-move-deletion-and-revocation), [Thread/AddressSpace contracts](nucleus_capabilities.md#thread-and-addressspace-contracts), and [lifetime/authority decisions and research](lifetime-and-authority.md). Prerequisites: D2–D5 as applicable, plus D1 before protection-context bindings.

Maintainer direction is partially resolved: keys name capability incarnations; Retype origins carry delegable lifetime-control permission; creators retain their own authority after delegation; SPeCK-like resource mechanisms support trusted KeyMaster derivation management and kernel object retirement; abandoned allocations may leak without kernel recovery. Correctness comes before representation optimization: change object/key fields and layouts as needed, updating all dependent calculations/views/tests; optimize in a later measured pass. Remaining schemas/mechanisms are still open, and no implementation is marked complete by these decisions. Excluded operation families remain intended functionality, not rejected designs.

Maintainer foundation decisions (2026-09-06): ordinary keys use implicit caller-table context, with initially 32-bit slot and 32-bit incarnation fields and separate shared-object identity, without freezing total key size permanently. Optional embedded type remains a proposal and would take 8 slot bits, not incarnation bits. Capacity is fixed for now through an easily changed constant; runtime resizing is outside initial scope. Move yields a destination-local key and invalidates the source on commit; generations must not silently wrap. All managed storage/metadata comes from accounted Untypeds, with retyped KeyTable backing made kernel-private. Enforce single-core execution and defer SMP; use short-lived guarded access and explicitly handle aliased operands even under the kernel lock. Table management follows ordinary source/destination capability permissions without manager-identity exceptions. Kickstart establishes initial Untypeds/KeyTables and hands authority onward. Follow-up choices: derive rather than mutate authority in place; exhaust only the slot when its 32-bit incarnation is consumed, retaining deletion; shared inconsistency error with diagnostic reasons; incarnation-checked management selectors; separate table-management permissions; vacant destinations and rejected same-slot Move; initial target-kind allowlist of KeyTable and debug-gated DebugConsole. Retype uses only an Untyped's unused watermark range with no outstanding access; it does not reclaim or unmap arbitrary live allocations. These decisions complete no implementation or validation checkbox.

Approved key package (2026-09-07): packed incarnation-high/slot-low 64-bit keys without a type tag; non-owning typed handles; increment on committed installation from 1, retained counters on deletion and slot-local exhaustion; InvalidKey/InconsistentKey/KeySlotExhausted statuses 26–28 with diagnostic reasons; CopyDerive register packing and destination-local results; no live-Domain logical table rebinding; independent 64-bit kernel allocation generations; explicit actual-key bootstrap handoff and coordinated rebuild without slot-only fallback. See the canonical contract for exact encodings. Concrete guarded metadata/backing, rights, bootstrap mechanism and domain integration remain work. Prototype code may be replaced rather than preserved as a compatibility constraint; pre-existing design-intent comments remain protected.

Guarded key-space package (selected 2026-09-23, not yet implemented): the key's low 32 bits become a table-relative address — a userspace-chosen per-table guard in the top `32 − size_bits` bits above the `size_bits`-wide slot index. KeyTable `size_bits` at Retype selects the capacity (1..=20, i.e. 2..=2^20 entries; a Thread's implicit table needs the well-known bootstrap slots, so at least 4 entries; the boot table keeps 256). The guard is stored in the KeyTable capability payload `{address, guard, size_bits}` (kernel-visible only), copied verbatim on derivation; every key minted into a table carries that table's guard; the caller's self-table guard is sourced from the `SELF_KEYTABLE` capability, whose absence or mismatch is a defined rejection; destination slot arguments stay bare indices; guard mismatch is InvalidKey reason `GuardMismatch = 4`, checked after zero-incarnation and before slot bounds; the KeyTable Retype argument packs the guard into `x3` bits 39:8 above the `size_bits` byte (zero for other kinds), a batch shares one guard, and the carve size is derived from `size_bits`. Guards are namespace values, not secrets — they bind keys to their table rather than hiding entries from a table's own users.

### Protected Procedure Call: Invocation design and migration

Maintainer selection: `Invocation` is a Protected Procedure Call (PPC). It identifies a component API entry point in a target AddressSpace, and the source Thread migrates into that AddressSpace; no server Thread is required. `Invocation.Call` is op `0`, with six `u64` Call inputs in `x2..x7` under the common `CapInvoke` ABI. The target component/export setup selects and publishes a nonempty stack extent when constructing the Invocation. At Call, the target entry SP is 16-byte aligned and checked against that published extent; the extent/headroom inputs use `x5` base, `x6` exclusive end, and `x7` positive minimum headroom as a direct `u64` byte count, representing `[base, end)` and rejecting `base >= end`. Call requires 16-byte-aligned `SP`, `base < SP <= end`, and `SP - base >= M` for positive minimum downward headroom `M` published by the target at CreateInvocation and stored in the Invocation. Its byte-count encoding and alignment are selected: `base`, `end`, and `M` are each multiples of 16 bytes, without requiring page alignment. Construction rejects `M > end - base` before installing a capability; equality is valid. Stack validation uses the selected `InvalidStack` family: `x1` offending `u64` value and `x2` field-specific typed reason, without operand packing. Status 32, the catalogue, reason IDs 1–12 (0 invalid), offending-value rules, stack-predicate order and admission-stage placement are selected in the canonical contract. The kernel checks the published range only, not its page mappings or whole-stack writability. The target SP uses an ABI channel separate from target function arguments; target-entry `x0` and `x1` are two leading dummy arguments ignored by the target, and the six real `u64` inputs stay unchanged in `x2..x7`, without a register shuffle. None carries SP metadata. The integer result payload is two `u64` words, separate from kernel transport status; successful source resumption uses `x0 = SUCCESS (0)`, `x1 = r0`, `x2 = r1`. The common extern-C body return of a repr-C two-u64 struct in x0/x1 is experimental; freezing it is a pending maintainer decision. `Thread.Return` is op `0` on the explicit `CurrentReturnOnly` Thread selector; Return SVC inputs are the target-table-local packed Slot(1) key in x0, x1=0 and payload r0/r1 in x2/x3. Return ignores x4..x7; the low-level helper is fallible (Result<Infallible, CapError>). The common adapter routes Err with original payload to a non-returning libOS fault handler; userspace binding is provisionally link-resolved and the five-word extern-C handler ABI is selected, the handler symbol is `vesper_thread_return_fault`, unexpected local SUCCESS uses selected `UnexpectedReturn` status 34. Conservative x0..x17 compiler declarations are selected; x18 is caller-volatile with discarded wrapper clobbers; FP/SIMD is prohibited/trapped for this slice; kernel non-payload GPR/NZCV scrubbing and target-status inheritance are selected, not implemented/validated. Call inherits source saved SPSR mode/masks/other non-NZCV controls, never live kernel-handler status; Return restores exact raw saved source SPSR. The working Call-time SP transport is provisionally selected as `x9`, read from saved `frame.gpr[9]` in the kernel, and freezing it is a pending maintainer decision. Userspace may compose queued rendezvous over Invocation plus Notification/EventCount. The former rendezvous/reply-object model is replaced. The selected relative timeout for Notification.Wait and EventCount.Await remains unchanged.

**Approved representation-only scope:** `KeySlot::THREAD_RETURN` stays Slot(1), all other slots stay unchanged, and kind IDs remain `Thread = 3` / `Invocation = 7`. The Return cap has explicit `CurrentReturnOnly` selector, never `Named(ObjectId)`, with no function/AS/concrete Thread target or Thread-management rights. Named Thread entries do not authorize Return; the current-relative form rejects Grant/Suspend/Resume/Retire and object_id extraction. Ordinary caller-table/SELF, guard, incarnation, bounds and presence checks remain mandatory: no magic raw key or lookup bypass. Any Thread may invoke the same AS-shared sentinel, but only its own current invstk top may be popped; AddressSpace provisioning installs it before activation. Invocation is Call-only with mandatory `NonZero<u64>` function address, not Option; CreateInvocation zero remains `InvalidPointer`. Opcode zero on an ordinary Invocation is Call, not wrong-form Return; Thread.Return on a named Thread is `InvalidOperation`, and unknown Invocation op 1 is `InvalidOperation` when the Call handler is enabled (kind currently unsupported). No compatibility alias or old Return opcode is retained. Current-contract descriptions below follow the canonical document; older validation is historical evidence only, not validation of this migration.
