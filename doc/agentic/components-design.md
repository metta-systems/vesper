# Components design

The rules for EL0 components: Meddle interfaces and imports, how Kickstart wires a component
to its exporters, the device memory, mailbox and PCI resources Kickstart hands out, and the
shell and component loading. Open questions and future work are in
[components-decisions.md](components-decisions.md), open work in
[components-implementation-plan.md](components-implementation-plan.md), finished work in
[components-completed.md](components-completed.md). Capability semantics (Invocation, `Call`,
`CallWithKey`, `Thread.Return`, badges, stack pools) are in the
[capabilities contract](capabilities-contract.md#invocation-protected-procedure-call).

## Decisions

### Component interfaces and imports

A component's interfaces are Meddle files in its `interfaces/` directory: one `<name>_vN.if` per exported interface version and an `imports.if` of `uses <interface> via device <link>, ... { function, ... }` or `uses <interface> via component <name> { function, ... }` declarations. `libs/meddle` generates the interface crate (trait, decoding, one `ppc_export!` entry `<interface>_<function>` per function) and the client crate (typed calls). The call convention is the userspace convention in `libs/meddle-runtime`: arguments flattened into `x2..x7`, unused words zero, and the answer `r0..r5` = the outcome and five words, outcome 0 for success, `n` for exception `n - 1`, `u64::MAX` for undecodable arguments. **Several results (maintainer decision, 2026-11-23, C2(a)):** a function declares any number of results, and an exception any number of fields, flattened in declaration order into `r1..r5` (at most five words; unused words zero, checked by the client like unused argument words); each value keeps its own words, with no packing. A generated function with several results returns them as a tuple in declaration order.

- **Return key (maintainer decision, 2026-10-12):** the component builder hands a component its provisioned `Thread.Return` key in its init record (for a Kickstart driver, `DriverInit::return_key`); an exporting component records it with `export::init_return_key` before answering (the generated trait's `enter` hook).
- **Choosing the exporter (maintainer decision, 2026-10-12):** an import is linked through the device tree: `via device` names the chain, and Kickstart reads the client node's property the first step names, takes its first cell as a phandle, and binds the import to the loaded instance whose node has that phandle and which exports the interface at the same type code. A chain `via first, second, ...` resolves the link step by step, each property read from the node the previous one reached, so a client can reach its exporter through an intermediate node (a firmware-service node through `firmware, mboxes` to the mailbox). **Providers without a link (implementation choice):** the first step may instead be `device compatible "string"`, the one enabled node with that compatible string, for exporters no property of the client leads to (the power management node reaching the mailbox through the firmware node, any client reaching `power_v1` or `fb_v1`); later steps follow properties as before. An import with no such instance is not granted, and the client's call reports it as not granted. Taking the first cell is the current rule; consumer properties with several providers are not distinguished yet. **Naming a component (maintainer decision, 2026-10-18):** `via component <name>` names a manifest component, which is the namespace until a namespace entry replaces it. The exporter is the one loaded instance of that component that exports the interface at the same type code: none leaves the import not granted, and more than one is reported by Kickstart and not granted, never resolved to the first. Only `via device` takes a link chain. The spellings without `device` are not accepted.
- **Target stacks (maintainer decision, 2026-10-12):** the exporter reserves one guarded stack for each (client instance, exporter instance) pair, shared by every function the client imports from it, so a client calls one exporter from one Thread at a time; the generated client's `ExclusiveStacks` proof states that obligation.
- **Delivery (maintainer decision, 2026-10-12):** Kickstart creates one `Invocation` per imported function in the client's table and records it in the client's init record (`DriverInit::imports`, at most 32), each as `{type_code, function index, Invocation key, target stack end}`; the generated `Bindings::from_imports` selects its interface's records by type code.
- **xbuf data areas (maintainer decision, 2026-10-12):** for an interface whose functions pass references (`T&`, an IoRec into a data area), Kickstart's import wiring also creates the data area for each (client instance, exporter instance) pair, mapped at the same virtual address in both. The interface declares its size. **Declaration and layout (implementation choice):** the interface file says `data <bytes>;` (whole pages, at most 64 KiB; required exactly when a function takes a reference). Kickstart carves the pages from the boot Untyped and maps them read/write in both components at consecutive addresses of one 2 MiB window (`DATA_WINDOW_VA`), each pair at the next free address, so an address means the same to both; it keeps the Frame capabilities, so neither side can unmap the area. The client finds its area in its import records (`ImportRecord::area_base/area_len`, `Client::data_area`), the exporter in `DriverInit::areas` with the stack reserved for that client. A reference is one IoRec per call. A call runs to completion on the caller's Thread, so the exporter touches the area only during the call and no completion EventCount is needed; asynchronous submit and complete is future work.
- **Telling clients apart (maintainer decision, 2026-10-19):** Kickstart badges each client's import keys with the base of the area it shares with the exporter (nonzero and unique per pair; the client holds the key with `CALL` only, and a badged key cannot be badged again whatever its rights; a pair with no shared memory gets an unbadged key). An interface whose exporter needs its caller says `badged;`, so its functions receive the badge of the key they were called through, and the exporter finds the client with `DriverInit::area_for_badge`; it accepts references only inside that client's area. The stack a call runs on says nothing about the caller. A resource the exporter hands out itself (a pipe) carries its own badge, and the exporter records which client created it.
- **Interface versions (maintainer rule, 2026-10-13):** while no production code uses Meddle interfaces, a change to an interface edits its `<name>_vN.if` in place; the version number is bumped only for an interface the maintainer declares to have production users.
- **Lending a key through an interface (maintainer decisions, 2026-10-13):** a function that lends a key through [`CallWithKey`](capabilities-contract.md#callwithkey-invocationcallwithkey-op-1) says so in a clause `lends (<kind> <name>)` after its parameters and before `returns`: the key travels in `x8`, outside the six data words, so it is not a parameter. The kind comes from a closed set matching the lendable kernel kinds (`key_table`, `frame`) so that the generated client and server are strongly typed; an untyped key is not offered. The placement window is declared per interface, not per function. **Concrete form (implementation choice):** the interface declares `placement <slots>;` (required exactly when some function has a `lends` clause, from one to eight slots), only `local` interfaces may lend, and a function lends at most one key. Kickstart reserves that many contiguous, never reused slots in the exporter's table for each (client, exporter) pair, and every `CallWithKey` Invocation of the pair declares that window; one slot matches the one-Thread-at-a-time stack of the pair. The generated Rust puts the lent key first in client method and server trait signatures, ahead of the data parameters. The server can neither inspect the kind nor the rights of the key it receives, so a kind or rights mismatch surfaces when it uses the key.
- **Resource keys through an interface (maintainer decisions, 2026-10-19):** an exporter hands out a resource (a USB pipe) as Invocation keys, one per function of a `local` interface of its own (`pipe_v1`), so each function keeps all six argument words, can be delegated separately, and holding a key is the right to use the resource. The interface says `badged;`, and its generated server functions receive the badge of the key they were called through as their first parameter (the resource's handle). A function of another interface delivers the keys: it has a `lends (key_table <name>)` clause and an `installs (<interface>)` clause after it, takes a `card32 first_slot` parameter, and returns the keys' wire values through the data area (`data` is required), because a slot's incarnation is not predictable once slots are reused. The exporter keeps one master Invocation per function in its own table, created lazily on first use from its own `AddressSpace` key (`GRANT`) on its stack pool, and derives a badged copy with `CALL` only (`BADGE` and `LEND` withheld) into the lent table at consecutive slots from `first_slot`, which needs only `INSTALL` on the lent key. Closing the resource retires its badge generation, so every copy of its keys fails from then on; the copies stay in the holders' tables until deleted. The generated export macro also defines `<interface>_entries()`, the entry addresses the exporter creates its masters from. Meddle generates no installing code, but it reads the installed interface's file from the include directories the caller lists explicitly and cross-checks it (`local`, `badged;`, not empty, same data area size as the installing interface), and the installed interface's fingerprint is part of the installing interface's type code.
- **Channels through an interface (maintainer decisions, 2026-10-19):** a `local` interface can declare `channel <pages>;` (1 to 16 data pages). Kickstart provisions one io-channel (`libio-channel`: a control page and that many data pages) for each (client, exporter) pair, right after the pair's data area and at the same address in both, and records its control page in the client's `ImportRecord::channel_base` and the exporter's `ExportedArea::channel_base` (zero: none); the page count is the interface's `CHANNEL_PAGES`. The channel is per client, not per pipe or function: what travels on it says which resource it belongs to in the packet's value word. How channels are provisioned for components in general is future work (see [components-decisions.md](components-decisions.md#future-work)).

- **GPIO pin functions (maintainer decision, 2026-10-22):** one `gpio` component owns the GPIO block (`brcm,bcm2835-gpio`) and exports `gpio_v1`: `set_function` switches a pin to input, output or one of its alternate functions (`pin_function`; `PinFunction::from_select_code` reads the device tree's `brcm,function` code), `set_pull` pulls a pin up or down or neither (`pin_pull`; `PinPull::from_code` reads `brcm,pull`), and pin levels follow when a client needs them (`power`'s power-down). **Pin groups (maintainer decision, 2026-10-22):** the device tree says which pins a node uses: Kickstart copies the pins of the node's default pin state (`pinctrl-0`), with their functions and their pulls where the group sets them, into the driver's init record (`DriverInit::pins`), and a driver whose device needs its pins routed imports `gpio_v1` and sets them up when it starts, pull first (`sdhost-bcm2835`: GPIO 48 to 53 to ALT0 on the Raspberry Pi 3). Kickstart itself switches no pins, and no other driver maps the GPIO page.

### Device memory Kickstart hands out

Kickstart hands out device Untypeds covering the device-tree MMIO ranges, excluding every range the kernel drives itself: the interrupt controller (GIC or BCM controller), the per-core timer and mailbox block, and any other kernel-owned device; as in seL4, a component can never map kernel-used device registers, with the Raspberry Pi mailbox below as the one exception. What Retype does with a device Untyped is in the [capabilities contract](capabilities-contract.md#allocation-and-representation).

- **Device Untyped placement (maintainer decision, 2026-10-11):** Kickstart installs the device Untypeds in a contiguous range of boot-table slots and records the first slot and the count in `BOOT_INFO`; a separate table is not used, since only Kickstart and the boot phase read the range.
- **Device Untyped coverage (maintainer decision, 2026-10-11):** each enabled node's register range is rounded out to whole 4 KiB pages, pages shared by several nodes are merged, and each run is split into the largest aligned power-of-two blocks, so no two device Untypeds overlap; a page touching a kernel-owned range is withheld whole, along with every other device on it.
- **ARM local interrupt block (maintainer decision, 2026-10-11):** the `brcm,bcm2836-l1-intc` block is withheld on every board, even where no loaded component drives it (the Raspberry Pi 4), because it is an interrupt controller and also holds the core timer controls.
- **Other interrupt-controller nodes (maintainer decision, 2026-10-11):** for now no other node is withheld for being marked as an interrupt controller; such nodes (for example the Raspberry Pi 4 `rpivid-local-intc` of the video decoders) are handed out like any other device.
- **Video memory (maintainer decision, 2026-10-12):** the framebuffer lives in `VideoCore` memory, which no device-tree node and no RAM Untyped covers. Kickstart infers it from the memory map: from the top of the RAM the device tree lists to the lowest device register, rounded down to 1 MiB and at most the first gigabyte (`VideoCore` reaches no further), and installs it as device Untypeds, split into aligned power-of-two blocks, ahead of the register Untypeds. A driver whose manifest entry says `video_memory = true` receives them (`DriverInit::video`); today that is `fb`, which checks that the framebuffer the firmware allocated lies in them. This is a heuristic: it matches the firmware's answer on the emulated boards (`0x3c000000` up to the peripheral window on the Raspberry Pi 3 and to `0x40000000` on the Raspberry Pi 4) and has not been checked on hardware. The Raspberry Pi 4 uses the same component.

### Raspberry Pi mailbox (maintainer decisions, 2026-10-12)

- **The mailbox component:** the VideoCore mailboxes share a 4 KiB page with the BCM interrupt controller, so that page stays out of the device Untypeds. The mailbox is served by the `mailbox` component, an EL0 component in the TCB that drives the `brcm,bcm2835-mbox` node and exports `mailbox_v1`: Kickstart hands it a device Frame for the shared page, the one exception to never mapping kernel-used device registers.
- **Kernel-owned page grants:** Kickstart keeps a list of the compatible strings whose drivers receive a device Frame for a kernel-owned page their node touches (today only `brcm,bcm2835-mbox`), special handling like the withheld interrupt controllers; on the Raspberry Pi 4 the page is not kernel-owned and the component loads as an ordinary driver. Other components reach the mailbox only through Invocations of its `mailbox_v1` functions, granted per function as their `interfaces/imports.if` declares; no kernel capability kind represents the mailbox.
- **Mailbox clients:** the firmware-service components (`fb`, which drives the framebuffer node, and `power`, which drives the power management node; later `cprman`, `axiperf` and `vcsm`) import `mailbox_v1`; their nodes link to the `raspberrypi,bcm2835-firmware` node through `firmware` (or, for the power management node, which has no such link, it is found by compatible string), and Kickstart resolves on through that node's `mboxes` link to the mailbox instance.
- **Property buffers (maintainer direction):** `property` accepts only a whitelist of tags known to be safe for any client: read-only queries and the display configuration tags. Everything else is refused, including every tag that hands over the system and the tags that change clocks or power (typed functions or per-client policy cover those); the list grows as components need tags.

### PCI (maintainer decisions, 2026-11-13 and 2026-11-14)

- **PCI host bridges:** the outbound memory windows of every enabled PCI host bridge (`device_type = "pci"`, its `ranges`) become device Untypeds like the register ranges. A driver whose manifest entry says `pci_host = true` receives them (`DriverInit::pci`), with its node's parsed outbound and inbound (`dma-ranges`) windows, the first register range of its MSI controller when `msi-parent` names another node, and the first register range and specifier of every reset its node's `resets` names; it pulses those resets itself. MSIs are set up from the start. Where another controller turns each MSI vector into its own interrupt line (the BCM2712 MIP), the driver gets only the last vector's line, for a self-test that raises it from software.
- **PCI child drivers (2026-11-14):** Kickstart loads the drivers for functions behind a host bridge at boot, like any driver, from the device-tree nodes below the bridge; a node without `compatible` (the Raspberry Pi 4 VL805, `usb@1,0`) is matched by a manifest entry naming its device-tree path. Each child imports `pci_v1`, exported by the host bridge driver, and the badge of its Invocation key names the child; Kickstart lists each badge with the PCI address of the child's node in the host bridge driver's `DriverInit`. A child gets its BARs by calling `claim` through `CallWithKey`, lending its own KeyTable (`INSTALL | LEND`): the host bridge driver carves device Frames for them from its window Untypeds into the child's table, returns their bus and CPU addresses and sizes, and only then enables memory decode and bus mastering for that function. Where the bridge itself turns MSIs into one interrupt line (the BCM2711), the host bridge driver demultiplexes them: Kickstart installs in its table, for each child, a badged key that signals the child's Notification with the child's MSI bit. Where each vector has its own line (the BCM2712 MIP behind RP1), the host bridge driver programs RP1's MSI-X vector *n* to MIP vector *n*, and Kickstart binds the MIP line of every interrupt an RP1 child's node lists (RP1 interrupt *n*) to that child's Notification at boot, as for any interrupt. RP1's children reach their registers, which lie in RP1's BAR1, through `claim` too: the host bridge driver places BAR1 at the bus address the `rp1` node's `ranges` give and hands out the sub-ranges the child's node lists.

### The shell and loading components (maintainer decisions, 2026-10-13)

The shell is the first EL0 component without a device node. It ports the commands of `userspace/shell.rs` the maintainer marked: `help`, `led on`, `led off` (through the mailbox), `draw` (the former `disp`: it paints some static graphics, text and shapes, and the first time releases an extra Thread of the shell that keeps rendering lava blobs, metaballs, continuously) and `end`. `feats`, `mmu`, `map` and `trap` are not ported. It lives in `userspace/shell/`.

- **`[[component]]` loading:** Kickstart loads the `[[component]]` entries of its image (today only test builders load them), with their imports. An entry can ask for extra Threads, since the shell needs one for background framebuffer rendering.
- **Console wiring:** Kickstart ports the uart test builder's attachment of a client to a PL011 driver (see `libserial-channel`) and connects the shell to the PL011 for now; there is no general mechanism yet.
- **Framebuffer window:** Kickstart gives the component that owns the display (the compositor) the page tables and table entries it needs to map the framebuffer's Frames when it wires the component up. A 1024 by 768 display fits in about two 2 MiB Frames.
- **Fonts as resources:** the boot image carries a `[[resource]]` entry, a new kind of image content that Kickstart wires up; a component names the resources it maps in a `resources = [...]` list of its manifest entry. Kickstart maps each read-only at `libimage::RESOURCE_BASE` (page-aligned, one after another) and reports `(base, len)` in `DriverInit::resources` in that order. (The maintainer expected the shell to name the font in `uses`; the manifest list is the current form, pending that decision.)
- **Framebuffer window:** a component that imports `fb_v1` receives, in `DriverInit::map_window`, its second-level `PageTable` and four uninstalled last-level `PageTable`s, and the 8 MiB span at `FB_WINDOW_VA` to map in. It lends a table of its own to `fb_v1.frames`, copies each Frame out of it (with `GRANT`, to learn its extent) and maps it at `FB_WINDOW_VA` plus the Frame's physical offset from the 2 MiB boundary below the framebuffer, so every Frame is aligned for its size: a 2 MiB Frame is a block in the second-level table, and a last-level table is installed (`PageTable.Map`) only for a span holding 4 KiB Frames. The mapping is write-combining (`libframebuffer`, used by the compositor).
- **Surface window:** a component that imports `compositor_v1` receives, in `DriverInit::map_window`, its second-level `PageTable` (the last-level tables are zero) and `SURFACE_SLOTS` ranges of `SURFACE_SPANS` 2 MiB spans from `SURFACE_WINDOW_VA`, `SURFACE_SLOT_BYTES` apart, to map the Frames of its windows' surfaces in. The compositor carves a surface's 2 MiB Frames from its own Untyped, maps them in the same range of its own `AddressSpace`, and installs a copy of each (`READ | WRITE | GRANT`) into the table the client lends to `compositor_v1.create_window`; a surface is its bytes rounded up to a multiple of 2 MiB (maintainer decision, 2026-10-19). A surface's Frames are never taken back, since the client may still hold them.
- **LED:** `mailbox_v1` gets a typed `set_led(boolean on)`; the difference between the Raspberry Pi 3 and 4 is hidden behind it.
- **Colors:** ported from the kernel-era display code; a more flexible type may follow.
- **Write-combining mappings for device Frames:** provided by the [Frame memory attributes](memory-design.md#frame-memory-attributes-maintainer-decision-2026-10-13): `fb` carves the framebuffer Frames with a `WriteCombining` ceiling.
