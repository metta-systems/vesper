# USB completed

Short markers of what is done, grouped by plan phase. Each line says what exists and where it is exercised. Rationale and details are in the [design](usb-design.md); the history of how each piece landed is in version control.

## USB0: design and interfaces

- [x] Interfaces `usb_hcd_v1` (`drivers/usb-hcd-dwc2/interfaces`), `usb_v1` (`drivers/usb/interfaces`) and `input_v1` (`drivers/usb-hid/interfaces`) parse under `meddler check`.

## USB1: pure protocol logic

- [x] `drivers/usb/protocol` (`vesper-usb-protocol`): setup packets, descriptor walker, enumeration state machine, HID boot-report decoder; no I/O, no allocation. Exercised by `just test-usb-host`, linted by `just clippy-usb-host`.

## USB2: DWC2 root port and EP0

- [x] `drivers/usb-hcd-dwc2`: register map on `bitbybit` fields and a `derive_mmio` block, the control-stage plan, and an EL0 component that resets the root port and runs EP0 control transfers by DMA through a driver-owned, cache-maintained page. Exercised by `just test-usb` (QEMU raspi3b, hub on the root port, reported as class 9 at address 1).
- [x] Only the root device is enumerated (by the client, over `usb_hcd_v1`).

## Shared changes

- [x] `libs/device-driver`: `MAX_DEVICE_PAGES` is 32 (Pi 3 DWC2 node: 64 KiB window plus a 4 KiB range). Exercised by `just test-driver`.
- [x] `libs/serial-channel`: `CONTROL_VA` is `0x3802_0000`, above the 32 register pages. Exercised by `just test-uart`.
- [x] `Justfile`: `usb-hcd-dwc2` and `usb-test-client` in `user_components`, `usb-hcd-dwc2` in `driver_components`; recipes `test-usb-host`, `clippy-usb-host`, `build-usb-test`, `test-usb`. The USB crates, the generated `usb-hcd` and `usb-hcd-client` and the test client are in the `Cargo.toml` workspace.
- [x] `libs/meddle-runtime`: `DataArea::read_bytes` and `write_bytes` for byte-granular access to a shared data area. Exercised by `just test-meddle` and `just test-usb`.
- [x] `drivers/usb/protocol`: `SetupPacket::from_bytes`, the inverse of `to_bytes`. Exercised by `just test-usb-host`.

## USB2 follow-ups

- [x] `usb_hcd_v1` control pipes served by `drivers/usb-hcd-dwc2` (generated `server` and `client` crates): `reset_port`, `port_status`, `open_pipe` (control only), `set_route` (stored), `close_pipe`, `clear_halt`, `control`. Pipes are a 16-entry table of generation-checked handles. Exercised by `just test-usb` (`usb-test-client` enumerates the hub through the import and checks refusals) and the host tests of `pipes`, `control::data_length` and `port_status_bits` (`just test-usb-host`).
- [x] `pipe_v1` keys: `usb_hcd_v1.open_pipe` installs the pipe's functions as Invocation keys badged with the pipe handle in the caller's lent table, so holding a key is the right to use the pipe. Exercised by `just test-usb` (copied keys, close through a copy, stale keys) and `libs/device-driver/tests/masters.rs`.
- [x] `pipe_v1.configure`: a pipe is opened to an endpoint address (direction in bit 7), then configured with kind, packet size and interval, again when a device's control packet size is learned. Exercised by `just test-usb` and the `Config` host tests (`just test-usb-host`).
- [x] Split transactions in `drivers/usb-hcd-dwc2`: `control` on a pipe with a route (`pipe_v1.set_route`) runs each packet as a start split and complete splits through the hub (`split::Sequence`: NYET repeats the complete split, a NAK or error starts the packet over, bounded), with the `HCSPLT` register and the NYET and frame-overrun interrupts in `regs.rs`. Exercised by the `split` host tests (`just test-usb-host`); not exercised end to end, because QEMU's controller has no transaction translator (`just test-usb` checks that a routed transfer fails cleanly).
- [x] Interrupt-driven completion in `drivers/usb-hcd-dwc2`: the component's Thread services the controller's interrupt (`HAINT`, `GINTMSK`, `HAINTMSK` and the channel masks in `regs.rs`) and advances a `completions` EventCount that control transfers sleep on, with a transfer deadline. Exercised by `just test-usb` (the client enumerates the hub; about 20 interrupts per run) and the register tests of `just test-usb-host`.

## USB3: hub and downstream devices

- [x] `hub` module of `vesper-usb-protocol`: hub descriptor parse, class request builders, `PortStatus` decode and the per-port `Port` state machine (power, debounce, reset, recovery, enumeration, teardown, `settled`). Exercised by the `hub` host tests (`just test-usb-host`).
- [x] `vesper-usb-host` (`drivers/usb/host`): `Pipes` (pipes made of the keys `open_pipe` installs, with slot groups) and `enumerate` (the enumeration state machine run over them, with an optional route and an observer of every control transfer). Shared by `usb-core` and `usb-test-client`; exercised by `just test-usb` and `just test-usb-core`.
- [x] `usb-core` component in `drivers/usb`: enumerates the root device, runs the hub driver (hub descriptor, port power, `Port` machines polled with `GET_STATUS`, enumeration and teardown of the devices behind it) with device addresses and a device table (`usb_core::devices`, host-tested), routes low- and full-speed devices behind a high-speed hub through `set_route`, and traces on the serial channel and under QEMU on semihosting. `usb_v1` is exported without claims. Exercised by `just test-usb-core` (QEMU: a hub on the root port and a keyboard behind it) and the `usb-core` host tests (`just test-usb-host`).
- [x] `transfer_failed` status of a failed split transaction marks the phase it failed in (`split::failure_status`); `usb-core` decodes the status in its trace. Exercised by the `split` host tests.
- [x] Meddle `channel <pages>;` and its provisioning: Kickstart maps an io-channel (control page and data pages) per (client, exporter) pair after the data area (`ImportRecord::channel_base`, `ExportedArea::channel_base`, generated `CHANNEL_PAGES` and `Bindings::channel`); `usb_hcd_v1` declares `channel 1;`. Exercised by the `channel` host tests (`just test-meddle`) and `just test-usb` (the client reads and writes the channel's pages).
- [x] `usb_v1` claims in `usb-core`: `badged;` interface, `claim_interface` never waits (`not_ready` until a matching unclaimed interface is attached, `busy` when the claim table is full), `release`, and `interrupt_pipe` writing the ten-byte `PipeParams` record (device, endpoint, speed, interval, packet size, route) into the claimant's data area so `hid` opens its own pipe; offers come from each enumerated configuration, claims end with `device_gone` on unplug, and the exports share the state with the enumeration Thread under a `Turnstile` (`drivers/usb/src/{claims.rs,main.rs}`, `drivers/usb/interfaces/usb_v1.if`). Exercised by the host tests (`just test-usb-host`) and `just test-usb-core` (the turnstile and offers run in the enumeration path; no QEMU client calls the exports yet).
- [x] Interrupt-IN in the DWC2 controller: `pipe_v1.configure` serves interrupt-IN pipes (packet size 1 to 1024, interval 1 to 255 ms, `no_bandwidth` past 80% of a frame), a second Thread (`poller_main`) polls the due pipes whose client has an empty buffer posted, one IN transaction on the shared host channel under the same turnstile as the calls (a NAK is no data; a stall stops the polls until `clear_halt`), and returns each report in the client's buffer tagged with the pipe's handle; Kickstart provisions an `EventCount` per channel (`ExportedArea::channel_event`, `ImportRecord::channel_event`, `ChannelArea::event`) that the controller advances and the client waits on (`drivers/usb-hcd-dwc2/src/{periodic.rs,main.rs}`, `drivers/usb/protocol/src/report_channel.rs`, `kernel/kickstart/src/drivers.rs`). Exercised by the host tests (`just test-usb-host`: schedule, bandwidth, poll outcomes, NAK sequence) and `just test-usb`, where the client reads the hub's status-change reports through the channel with a keyboard behind the hub; split polls are untested.
- [x] DWC2 bring-up on the Raspberry Pi 3: the driver powers the controller's domain through `mailbox_v1.set_power_state` (answer unchecked, QEMU does not implement it), a timed-out bring-up step is raised as `usb_hcd_v1`'s `controller_failed { step }` from every call instead of a panic, the root-port device wait is 3 s and non-fatal, and a NAKed transfer is retried for up to 1 s. Exercised on the board with `just boot-usb-core-test` (LAN9514 hub and its Ethernet enumerate) and by `just test-usb`.
- [x] `usb-core` port handling: one device on the whole bus waits at address 0 at a time (`Port::holds_default_address`, `defer_reset`), a port whose device failed to enumerate waits for the unplug and takes the next device (over-current stays off). Exercised by the `hub` host tests (`just test-usb-host`) and on the board with `just boot-usb-core-test`.
- [x] Nested hubs in `usb-core`: up to `MAX_HUBS` hubs are driven together, a hub found on a port gets its own control pipe and port machines, low- and full-speed devices are routed through the nearest high-speed hub's translator, and an unplugged hub takes its tree with it. Exercised on the board with `just boot-usb-core-test` (a high-speed hub behind the LAN9514 enumerates and is torn down on unplug).
- [x] Split control transfers on the Raspberry Pi 3: a low-speed mouse behind the LAN9514 enumerates through its transaction translator. The complete split of an OUT or SETUP carries no data, the start-split position is zero for control and interrupt (USB 2.0 §8.4.2.2, §11.17.2), a NAK starts the split over without counting as an error (bounded by time), and a low-speed device's first descriptor read takes all 18 bytes. Exercised on the board with `just boot-usb-core-test` and by the `split` host tests (the NAK rule by the host tests only).
- [x] Keyboard and mouse input on the Raspberry Pi 3: a low-speed keyboard and mouse behind a high-speed hub behind the LAN9514 are served by `hid` and their keys and motion reach `input-trace`, through split interrupt polls (each placed in the next (micro)frame, `HCCHAR.OddFrm` from `HFNUM`). `hid` requires `SET_PROTOCOL` and only traces a refused `SET_IDLE` (optional for a boot mouse, HID 1.11 Appendix G). Exercised on the board with `just boot-usb-hid-test`.
- [x] Traces of components without a serial channel: `libserial-trace` keeps their lines in a backlog drained through `usb_hcd_v1.trace` (relayed by `usb-core`), `usb_v1.trace` and `input_v1.trace`, which `input-trace` prints; the hardware boot tests wait for good after their report instead of stopping the CPU. Exercised on the board with `just boot-usb-hid-test` and by `just test-usb-hid`.
- [x] Hub ports driven by each hub's Status Change endpoint (USB 2.0 §11.12.1, §11.12.4): `usb-core` opens the hub's interrupt-IN pipe, reads the change bitmaps on the controller's report channel and reads a resting port's status only when its bit is set (`Port::waits_for_change`); debounce, reset and recovery stay timed, and a hub without the pipe is polled. Removed the 1 s channel stalls a NAKing hub `GET_STATUS` caused while devices report. Exercised on the board with `just boot-usb-hid-test` (plugs, unplugs and steady input) and by `just test-usb-core`, `just test-usb-hid` and the `hub` host tests.
- [x] `hid` component (`drivers/usb-hid`): claims the boot keyboard and mouse through `usb_v1`, sets boot protocol and the idle rate over a control pipe of its own, opens each interrupt pipe on the controller with the `PipeParams` the core gave it (vendor and product ids and the interface number included, `usb_hcd_v1.open_pipe` now also returns the pipe's handle), decodes reports into `Key`, `Rel` and `Sync` records (`decode.rs`), keeps a state per device and serves them as `input_v1.descriptor` and `snapshot` and as frames in the buffers each client posted on its `channel 1` (a client without a buffer misses the frame and its next one starts with `Dropped`); a device that went away is released and a `DeviceRemoved` published. `input_v1` lost `set_leds`; `input-trace` (`userspace/tests/input/trace`) is its consumer and `libs/serial-trace` the trace both it and `usb-core` use. Exercised by the host tests (`just test-usb-host`, `just test-input-host`: decoding, devices, snapshots, `State::for_each_down`) and `just test-usb-hid`, where `input-trace` reads the QEMU keyboard's descriptor and snapshot; typed keys (`sendkey` in the QEMU monitor) came through as `Key` and `Sync` records. `just boot-usb-hid-test` is the Raspberry Pi 3 image.
- [x] Lost and stuck keys: `hid` sets the keyboard's idle rate to 100 ms (`Set_Idle`, HID 1.11 §7.2.4; the mouse keeps 0), so a lost report is put right by the next repeat; the boot-report diff ignores `POSTFail` and `ErrorUndefined` reports like roll-over, and a usage listed twice is one key; the compositor's router presses, on a resync, a key the snapshot holds that the window never saw go down. Rate-limited counters: the controller's restarted periodic complete splits (a report the hub may have dropped), `hid`'s undecoded reports and frames an `input_v1` client missed, the compositor's dropped window deliveries and router overflow; the compositor's and Wood's key lines say how long after `hid` decoded the key. The input path runs at `Priority::INPUT` ([scheduling-completed.md](scheduling-completed.md#root-dispatcher-priorities)). Exercised by `just test-usb-host` (fast taps, overlapping keys, held keys, idle repeats, error reports), `just test-compositor-host` (`a_resync_presses_a_key_pressed_in_the_lost_records`) and `just test-wood`.
