# IRQ design

The rules for interrupt delivery: `IRQControl` and `IRQHandler`, the nucleus IRQ table, the
receiver Thread, and how Kickstart matches and loads drivers and wires their interrupts.
Open questions are in [irq-decisions.md](irq-decisions.md), open work in
[irq-implementation-plan.md](irq-implementation-plan.md), finished work in
[irq-completed.md](irq-completed.md). Background, not specification:
[irq-research.md](irq-research.md) (where the interrupt-controller driver runs, prior art).
The wire schemas of `IRQControl.Issue` and the `IRQHandler` operations are in the
[capabilities contract](capabilities-contract.md#object-operation-baseline); scheduling of
receiver Threads is in the [scheduling design](scheduling-design.md#decisions).

## Decisions

### IRQ delivery

`IRQControl` and `IRQHandler` are core kinds. Their semantics do not depend on the architecture; the interrupt controller is driven by the boot-selected privileged component (`libirqchip` operation table), so no controller-specific code sits behind the capabilities.

- **IRQControl.** A boot key installed for Kickstart, which moves it to the EL0 `irq-manager` component for good. `Issue` translates a device-tree interrupt specifier into a line through the component's `xlate`, configures the trigger from the specifier, and installs an `IRQHandler` for that line in an explicit destination table and slot. A line has at most one live IRQHandler; issuing an active line fails with `IRQ_LINE_ACTIVE`. The nucleus-owned timer line is never issued and reports the same status, which reveals nothing beyond "in use". IRQ authority comes only from IRQControl: memory cannot mint it. **Issue schema (maintainer decision, 2026-10-11):** a specifier is relative to a controller named by its index in the component's controller list — the root controller 0, cascaded controllers following in device-tree order; Kickstart records that order in `BOOT_INFO`, so the issuer maps a node's `interrupt-parent` to the index. The destination is a destination-table key plus slot, as for Retype, which leaves room for three specifier cells (the GIC and BCM specifiers need at most three).
- **IRQHandler.** Names one line. `SetNotification` records a Notification identity and badge in the nucleus IRQ table (the supplied Notification key needs `SEND`; its nonzero badge is the signalled bits) together with the receiver Thread. **No silent rebinding (maintainer decision, 2026-10-14):** `SetNotification` on a line that is already bound fails with `AlreadyMapped` and leaves the binding unchanged; rebinding is explicit, `Clear` first. `Clear` removes the binding. `Ack` enables the line; it is the only operation that does, so a newly issued line stays masked until its first `Ack` (Issue, SetNotification, Ack, then Wait). **Teardown and receiver (maintainer decision, 2026-10-11):** Delete never retires an object and the kernel does not count copies, so teardown is the explicit `Retire` (`RETIRE`): it clears the binding, masks the line, invalidates every copy of the key (`ObjectRetired`) and frees the line for a fresh Issue. SetNotification takes the receiver Thread only; the receiver's Time is the Time bound to that Thread by `Scheduler.ConfigureThread`, and a Thread without one is refused.
- **Delivery.** The nucleus claims the pending line. For a bound line it signals the Notification with the stored badge, masks the line and ends the interrupt at the controller (on the GIC, priority drop and deactivation together). An unbound line is masked and ended. The line stays masked until `Ack`, so a level-triggered device cannot storm before its handler runs.
- **Receiver Thread.** The driver's loader creates the driver's Thread, which waits on the bound Notification, handles the device and calls `Ack`. The driver's loader (Kickstart, later `irq-manager`) gives the driver a Time; the receiver Thread must own a Time derived from it, and the wakeup is reported to the responsible scheduler, which decides whether it preempts (see [`scheduling-design.md`](scheduling-design.md)). Interrupt work is never charged to the interrupted Thread. A wakeup of a dispatcher-managed receiver is an ordinary runnable event: its record is published and, if the mask asks for `THREAD_RUNNABLE`, the dispatcher is activated, so the scheduler (not the nucleus) decides whether the receiver preempts the running Thread.
- **Driver matching.** A driver component declares the device-tree `compatible` strings it serves in a link section of its own binary, as the interrupt-controller components do; the image manifest only names the binary. Kickstart (later a device manager) loads a driver per matching enabled node and gives it a device Untyped for the node's MMIO ranges, the node's IRQHandlers and a Time.
- **Driver loading (maintainer decision, 2026-10-11).** Per matching node Kickstart creates one driver instance with its own AddressSpace, and gives it:
  - **Thread:** one Thread, retyped, configured on the driver's Time and started at the driver's entry; it is the receiver. A driver declares further Threads with `driver_threads!`.
  - **Time:** a Time transferred from the boot Time: infinite by default, or the finite `budget_ns` the driver's manifest entry names (maintainer decision, 2026-10-17).
  - **Device memory:** the node's register pages as page-sized device Untypeds; a driver carves its device Frames from them. A page that several matched nodes touch is retyped once into a device Frame, and each of those drivers gets a copy of it; there is no trust distinction between Kickstart-loaded drivers for now.
  - **Memory:** a RAM Untyped split from the boot Untyped, sized by the manifest entry, with its physical base and the address at which the node's device reaches it through its buses' `dma-ranges` (for DMA buffers carved from it).
  - **Interrupts:** Kickstart issues each of the node's interrupts and creates one Notification; interrupt *i* signals bit *i* (a badged key Kickstart installs directly). Kickstart binds every IRQHandler to that Notification and the driver's Thread; the driver waits and acks. **Repeated lines (implementation choice, 2026-10-27):** a line the node lists more than once (the BCM2835 DMA node lists the line channels 11 to 14 share four times) can hold one IRQHandler only, so Kickstart issues it once, at its first position, and the later entries take no position.
  - **Handoff:** Kickstart retypes an init page, writes a record with the driver's keys and the node's register ranges and interrupts, maps it into the driver at a fixed address and passes that address in `x0` on the Thread's first entry. Kickstart never calls into the driver.
- **Notification only (maintainer decision, 2026-10-14).** Interrupt delivery targets a Notification and nothing else: the kernel knows only which line fired, and a Notification carries that. An IRQHandler cannot deliver to an EventCount; counting work (received bytes, xbuf queue entries) is done by the interrupt-handling Thread with ordinary `EventCount.Advance`.
- **Brand.** There is no separate event-target kind: a Notification plus its receiver Thread and that Thread's Time cover what a brand named.

Implementation status: the IRQ table, `IRQControl.Issue` and the four `IRQHandler` operations are implemented; Kickstart carves the table from the boot Untyped, sized by the component's line count, and installs IRQControl at `KeySlot::IRQ_CONTROL`. Driver matching and loading are implemented (`kickstart::drivers`); the real boot path loads the bundled drivers. The `irq-manager` component does not exist, and a woken receiver is announced to its dispatcher (there is no kernel run queue).
