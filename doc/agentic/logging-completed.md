## P-LOGGING-2: every component a client

- [x] The USB components are clients (2026-10-29): `usb-hcd-dwc2`, `usb_core` and `usb_hid` import `log_v1` (`interfaces/imports.if`); usb-core-test, usb-hid-test and usb-test list the log server's interface directory (top-level `interfaces`) so the imports stay unlinked there, as in kernel/kickstart, compositor-test and window-events-test. The volume policy is in the design doc (section USB log volume). Kickstart's driver Thread stacks went from 16 to 32 KiB (`STACK_PAGES`): `usb-core` overflowed 16 KiB under QEMU once its trace went to the log channel; the maintainer approved the 32 KiB stacks on 2026-10-29 ("keep 32k stacks"). Checked: `just _test-wood` (the UART file holds the controller's bring-up and port reset, a device the core enumerated and `usb-hid: serving a Keyboard`; 38 USB lines in a 12.5 s run, 33 of them in the first 0.76 s, 0 dropped); test-usb, test-usb-core, test-usb-hid, test-compositor, test-shell (all run by hand, logs in `target/usbclient-*.log`), test-window-events, test-audio, test-midi, test-dispatch, test-driver, test-mailbox, test-uart; `just _build-wood-test-hw`; clippy of the USB crates, `libserial-trace`, Kickstart and the wood-test kernel with and without `qemu`; `just _clippy-log`, `just _clippy-usb-host`.

## P-LOGGING-4: panics, faults and early output

- [x] The EL0 panic handler (`userspace/runtime`) puts `PANICKED: <component>: <message> at <file>:<line>` on the component's log channel through the reporter `liblog_client` registers (`libuser::set_panic_reporter`), best effort and bounded (retries, then up to 100 ms for the server and 50 ms for the UART), with a re-entrancy flag; components without a channel behave as before. Checked by `just _test-log` (log-test: `log_probe`'s first Thread panics; the UART file holds the line with the `E` level).
- [x] Faults: `liblog_client` exports the fault handler (`vesper_fault_entry`); Kickstart installs it at `FAULT_HANDLER` with a stack of its own for every image that exports it; the init record names the component and its Threads' stacks (`MAX_IMPORTS` 32 to 28 to fit); the handler logs `FAULT: <component> thread <n>: <cause> …`, naming a guard-page hit `stack overflow (guard page)`, and terminates the Thread. Checked by `just _test-log` (`log_probe`'s second Thread overflows its stack: `FAULT: log_probe thread 1: stack overflow (guard page)` on the UART) and `just _test-log-host` (`FaultReport`: 3 tests). Regressions: test-wood, test-midi, test-audio, test-window-events, test-usb, test-usb-core, test-usb-hid (by hand, logs in `target/panic-*.log`); `just _build-wood-test-hw`; clippy of the log crates (`just _clippy-log`, now with `log-probe`), `vesper-device-driver`, `vesper-user-runtime`, Kickstart, log-test and wood-test with and without `qemu`.

## P-LOGGING-5: serial console at boot (LOGGING-12)

- [x] Protocol (`libs/chainboot-protocol`): the console beacon `^B^B^B`, the ACK `^F^F^F`, `CONSOLE_WAIT` (a beacon every 250 ms for 1.5 s), `CONSOLE_CONFIRM_WAIT`, `HOST_CONSOLE_CONFIRM_TIMEOUT`, `CONSOLE_REQUEST_GAP`, the chainboot handoff (`HANDOFF_MAGIC`, `handoff_registers`, `kept_rate`) and `Run`; host tests in `tests/chainboot_protocol/console.rs` (encoding, an older host ignoring the beacon, timing).
- [x] `libs/boot-uart` (`vesper-boot-uart`): chainboot's GPIO, mailbox and PL011 code, shared by chainboot and Kickstart. `libboot` keeps `x1` and `x2` at entry (`loader_registers`); chainboot passes its handoff there at the jump.
- [x] Kickstart's early console (`kernel/kickstart/src/early_console.rs`): bring-up, the handoff check, the negotiation, early lines on UART and semihosting, handed over before the MMU goes on.
- [x] chainofcommand answers the console beacon with `--load-baud`; `--console` sends no kernel (`just console`). What arrives after a protocol exchange's last read is printed (it was dropped, which lost Kickstart's first lines after a load). Host tests: `cargo test -p chainofcommand`.
- [x] QEMU, by hand (logs in `target/kserial-*.log`): the production image with chainofcommand over TCP negotiates 187 500 baud (QEMU's UART clock is 3 MHz, so 1 500 000 is refused, which checks the refusal); chainboot loading it at 187 500 hands over and Kickstart keeps the rate; with no host Kickstart stays at 115 200. `just _test-wood` passes with the early lines ahead of the log server's.

## DebugConsole (LOGGING-13, LOGGING-14)

- [x] DebugConsole gated behind `debug_kernel` (handler, grant, boot use); its results are propagated and its wrapper no longer prints.
- [x] Hardware debugging aid: in a `debug_kernel` kernel every component Kickstart loads gets a `WRITE` console key (`DriverInit::debug_console`, slot 15) its panic handler prints on, and Write reads caller-virtual memory checked by `AT` at the caller's level and prints on the board UART outside QEMU (`kernel/nucleus/src/objects/debug_console.rs`, `kernel/nucleus/src/board_console.rs`, `userspace/runtime`); exercised by the nucleus `debug_console` suite, `capability-test` and `ppc-test`, and on the Raspberry Pi 5 by board-test's log probe (`just boot-board-test debug_kernel`); EL0 bytes are read with `LDTRB` because the Pi 5's Cortex-A76 sets PAN on exception entry.
